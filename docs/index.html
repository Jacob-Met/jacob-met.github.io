Research software for the work between data and a decision.

I study computer science and physics at Cal State Long Beach, with a minor in biology, and I’m preparing for MD/PhD training. Those education and training details are self-reported (public profile).

I build tools for difficult handoffs: recording a research session, keeping evidence beside a check, or making a simulated decision reviewable before anything changes. My public work includes CaptureSuite, CanvasPilot, TowerOps, and workflow-checks. Each project links to its source and states what its demo does not establish.

Research tools, built to inspect.

CaptureSuite

CaptureSuite is a Windows-first platform for multimodal research capture. A daemon owns session timing and state; versioned C++ and Python workers connect individual devices; the session is sealed into a package for quality checks and analysis (project scope).

The repository includes a simulator and a Lab Streaming Layer bridge for running without vendor hardware. Its quality-control demo uses generated data; it is not a hardware benchmark or evidence of clinical validity (documented limits).

CanvasPilot

CanvasPilot gives Canvas LMS a command-line and MCP interface. A local browser-session broker can bridge API gaps where schools disable API tokens; the repository describes the implementation, not a verified live school login or student outcome (project scope).

The offline demo runs on synthetic fixtures without a Canvas account. It does not validate real school authentication or student results (documented limits).

TowerOps

TowerOps is a synthetic air-traffic decision-support demo. Before its simulated state changes, deterministic checks project conflicts, check freshness, require approval, and verify readback; it is not operational ATC software and is not connected to aircraft (project scope; demo code).

Multi-agent Fan-out Engine

A small, sanitized Python reference core for planning independent work, recording dispatches, and routing by requested effort. Open the public repository

Question

How can a multi-part task be planned and dispatched while keeping dependencies, idempotency, and uncertain outcomes explicit? Read the project context

Approach

  1. Represent work as a validated dependency graph so downstream parts stay queued until prerequisites complete.
  2. Record each dispatch, stable idempotency key, route, state change, and reconciliation evidence in SQLite.
  3. Park an ambiguous submission as outcome_unknown and require external evidence before resolving it; do not replay it.
  4. Keep transport and authentication outside the reference core behind a Hub adapter protocol.

Boundary. The tests use an in-memory SQLite ledger and local fake adapter. The package makes no model-provider calls, remote-worker calls, production-capacity claim, dispatch-volume claim, or benchmark-scale claim. Scope and limits

Disclosure. The code and documentation were developed iteratively with AI assistance, then manually reviewed and exercised with the repository tests and local demo. Repository README

CaptureSuite offline QC path

An offline quality-control path runs over a copy of a bundled synthetic EMG/IMU mini-session and emits inspectable reports and a receipt without capture hardware or patient data. Open the public repository

Question

How can a reviewer inspect a quality-control workflow before connecting a device or personal dataset? Read the project context

Approach

  1. Copy the bundled synthetic mini-session to a caller-chosen new output directory.
  2. Check original-fixture and copied raw-source hashes before and after the QC run.
  3. Refuse an existing output path or output inside the source fixture rather than overwriting it.
  4. Emit HTML and JSON reports plus DEMO-RECEIPT.json with hashes and synthetic-fixture classification.

Boundary. The README states that this synthetic demo does not establish hardware performance, clinical validity, or full product readiness; CaptureSuite v1.0 targets Windows 10 21H2+ x64. No hardware performance or clinical validity is claimed here; this case summarizes public source behavior, not an independent test. Scope and limits

Workflow checks: synthetic records, visible evidence.

workflow-checks contains three Python standard-library demos for utility bills, freight billing, and physical-therapy authorizations. The records are generated; try the interactive sample UI, inspect the full output pages, and read the README for scope and limits.

Utility bills

The demo flags records such as mismatched payments, duplicate bills, overlapping service periods, missing bills, and unusual usage. It keeps the source rows with each check and queues clean unpaid bills for human approval; it does not issue payments (utility demo).

Try the interactive sample · Full generated outputs · Inspect the code

Freight packets

The freight demo drafts detention packets and invoice flags with calculations and evidence timelines. Missing or uncertain tracking evidence is held for a person; nothing is sent or invoiced (freight demo).

Try the interactive sample · Full generated outputs · Inspect the code

PT authorizations

The PT demo turns synthetic authorizations and visits into a prioritized worklist with reason codes, submit-by dates, and payer checklists. The patients are invented and payer rules are placeholders; it does not submit anything (PT demo).
